## 1. 背景与前置依赖

Spec A 完成后，代码只认 OSS key，但生产 DB 中存的仍是本地绝对路径，两者不兼容。**字段语义的切换是原子的**——同一个值不可能一半是路径一半是 key，因此代码上线与数据迁移必须在同一个窗口内完成。本 Spec 负责这个窗口。

本 Spec 依赖 Spec A 已交付的以下能力：

- `object_store` 的 `put` / `head` / `list_prefix`（迁移脚本直接复用，不另写一套上传逻辑）
- key 命名规则「本地 storage_root 相对路径 = OSS key」（使迁移成为直接映射，零转换逻辑）
- 三个新增 DB 列：`pre_vc_video_key`、`pre_cc_last_frame_key`、`pristine_last_frame_key`（Spec A 建列，本 Spec 填值）

## 2. 迁移脚本

`backend/app/scripts/migrate_to_oss.py`，按项目规范通过 `uv run --project backend python -m app.scripts.migrate_to_oss` 执行。四阶段可分别运行：

```
--scan      扫描 storage_root，输出待迁移清单（文件数、总大小、未被 DB 引用的量）
--upload    上传对象（可在线运行，不动 DB）
--backfill  回填 DB 路径字段 → key（需停写窗口）
--verify    校验 DB 中每个 key 在 OSS 真实存在
```

### 2.1 幂等性（硬要求）

- `--upload` 对每个文件先 `head_object` 比对大小 / CRC64，一致则跳过。中断后重跑只补差量。
- `--backfill` 依据值的形态判断是否已转换——以 `/` 开头为待转换的绝对路径，否则视为已是 key。因此可安全重跑。
- 失败条目写入报告文件，支持针对失败清单单独重试。

**验收标准：连跑两次，第二次报告的变更数必须为 0。**

### 2.2 需回填的字段

- `Shot`：`video_path`、`last_frame_path`、`custom_first_frame_path`、`target_last_frame_path`、`vc_audio_path`、**`custom_reference_paths`（JSON 数组）**
- `Project`：`storyboard_path`、`final_video_path`、`reference_voice_path`
- `ReferenceImage`：`storage_path`
- `ImageCandidate`：`file_path`、**`ref_paths`（JSON 数组）**

两个 JSON 数组字段需单独处理，是最容易遗漏的地方。

### 2.3 三个新列的初值推导 —— 只此一次的时机

Spec A 新增的三列，初值**只能在本地文件尚存时通过扫描推导**：

| 列 | 推导方式 |
|---|---|
| `pre_vc_video_key` | 本地存在 `output_pre_vc.mp4` 则填其 key，否则 NULL |
| `pre_cc_last_frame_key` | 本地存在 `last_frame_pre_cc.png` 则填其 key，否则 NULL |
| `pristine_last_frame_key` | 按原 `pristine_last_frame_path()` 逻辑：`last_frame_*.png` 中排除固定名备份后取 mtime 最新 |

注意执行顺序上的一个细节：Spec A 阶段 5 会删除 `pristine_last_frame_path()` 等本地路径函数，而本节需要它的 glob 逻辑。因此**迁移脚本内自行实现这段目录扫描**，不 import 旧函数——脚本本就只在切换窗口内跑一次，自包含反而更清晰，也不会因为旧函数被删而失效。

本地文件一旦清理，这些信息即永久丢失，**无法补做**。因此三列的填充必须在 `--backfill` 内完成，且不可跳过。填错的后果是 VC / CC 的还原链路对存量分镜失效。

### 2.4 未被引用的本地文件

`--scan` 会报告 storage 中存在但 DB 无引用的文件（历史中间产物等）。默认**一并上传**——简单、无损，且避免误判丢失有用数据；报告中单列其数量与体积供人工判断。上线稳定后可由第 5 节的巡检脚本识别清理。

## 3. 生产切换

### 3.1 执行顺序

```
1. 备份 DB（sqlite 直接 cp）+ 确认 bucket 版本控制已开启
2. 在线运行 --upload（不停服，最耗时的一步在此消化）
3. 停止服务
4. 再次运行 --upload 补增量（停服前最后写入的文件）
5. 运行 --backfill
6. 部署新代码（Spec A + 本 Spec）
7. 启动 + 运行 --verify
```

真正的停机窗口仅第 4~7 步，**与数据总量基本无关**——大头在第 2 步在线消化掉了。

### 3.2 回滚

恢复 DB 备份 + 回滚代码即可，**OSS 上的对象不删除**（保留下来对下次重试有用，且只占存储费）。

**迁移后本地 `storage/` 目录先保留一到两周**作为回滚保险，确认稳定后再清理。清理前需确认 2.3 的三列已正确填充——本地目录是这些信息的唯一来源。

### 3.3 验收

- `--verify` 全绿（DB 中每个 key 在 OSS 均存在）
- 人工抽查若干历史项目：视频可播放、尾帧可显示、导出的成片可下载
- 抽查一个做过 VC 和 CC 的历史分镜，确认还原功能正常（验证 2.3 的三列填对了）

## 4. 开发期协作风险

Spec A 第 8 节已确定开发期使用独立 DB 卷与独立 dev bucket。此处补充与本 Spec 直接相关的风险：

**一旦在共享 dev DB 上运行了 `--backfill`，字段即变为 key。此时把栈切回任何旧 worktree，旧代码会把 key 当绝对路径使用，媒体全部加载失败。** 这不是代码能规避的问题，只能靠环境隔离——这正是采用独立卷方案的直接原因。

## 5. 孤儿对象巡检（仅 dry-run）

Spec A 第 4.2 节的一致性规则（宁可留孤儿，绝不留悬空引用）会持续产生无人引用的对象。

**本次仅实现 dry-run 巡检脚本**：比对 OSS `list_prefix` 与 DB 中的全部 key 引用，输出「超过 N 天未被引用」的对象清单与总体积，**不执行任何删除**。

理由：它是整套设计中唯一具备不可逆破坏风险的组件。先用报告观察真实孤儿量与增长速度，再决定是否值得开启自动清理。若孤儿量微不足道，自动清理就不必做。

开启自动删除的前置条件（未来若要做）：bucket 版本控制已开启、dry-run 报告经过至少数周观察、删除操作本身也先跑 dry-run。

## 6. 运维侧待办清单

> **NOTE —— 以下均为 OSS 控制台 / RAM 控制台的配置项，不在代码范围内，需要人工执行。**
> 其中第 1、2 项是第 5 节「只做 dry-run」这一决策的直接依赖：因为不自动删除孤儿对象，**存储用量会随时间缓慢增长**，必须由生命周期规则兜底，否则存储费用会持续爬升且无人察觉。

| # | 事项 | 时机 | 说明 |
|---|---|---|---|
| 1 | **开启 bucket 版本控制** | 切换前（3.1 第 1 步） | 误删保险。是未来开启孤儿自动清理的前置条件 |
| 2 | **配置生命周期规则** | 切换后一周内 | 历史版本 30 天后转低频存储或删除。**这是不做自动 GC 时控制存储成本的唯一手段** |
| 3 | **bucket 保持私有读** | 创建 bucket 时 | Spec A 的签名 URL 方案依赖于此；若误设为公共读，签名机制形同虚设 |
| 4 | **RAM 策略最小权限** | 创建凭证时 | 仅授予目标 bucket 的读写权限，**不使用 `AliyunOSSFullAccess`** |
| 5 | **生产 ECS RAM Role 绑定** | 上线前 | 角色名填入 `oss_ecs_ram_role`，避免 SDK 反复请求元数据服务 |
| 6 | **确认 bucket 与 ECS 同地域** | 创建 bucket 时 | 同地域才能用内网 endpoint 免流量费；跨地域则 `oss_use_internal_endpoint` 必须保持 false |
| 7 | **设置存储用量告警** | 切换后 | 由于不做自动 GC，用量告警是发现孤儿异常增长的主要手段 |

## 7. 测试策略

沿用 Spec A 的原则：除计费模型调用外一律不 mock，测试打真实 OSS（dev bucket + 唯一前缀，teardown 删前缀）。

| 对象 | 做法 |
|---|---|
| **迁移脚本全流程** | 构造临时 storage 目录 + 临时 DB，跑完 scan → upload → backfill → verify |
| **幂等性** | **连跑两次，断言第二次变更数为 0**（2.1 的验收标准） |
| **JSON 数组字段** | 单独用例覆盖 `custom_reference_paths` 与 `ref_paths`，确保数组内每一项都被转换 |
| **三个新列的推导** | 构造「有 pre_vc 备份」「有 pre_cc 备份」「有多个 last_frame_* 需取最新」三种夹具，断言填值正确 |
| **中断恢复** | 上传到一半中断后重跑，断言只补差量且结果完整 |
| **巡检脚本** | 构造已知数量的孤儿对象，断言报告数量准确、且**确实没有发生任何删除** |

## 9. 实施阶段需要逐行核对的代码

1. **DB 字段清单的完整性** — 2.2 列出的字段来自对模型文件的检查，实施前需再次核对 `app/models/project.py` 全部路径类字段，确保没有遗漏（漏一个字段 = 该类资源全部失效）。
2. **`--backfill` 与建列的执行顺序** — Spec A 阶段 2 的三个新列由 `app/db.py` 的幂等 `ALTER TABLE` 在应用启动时创建（本项目不使用 alembic）。因此 3.1 的切换顺序存在一个隐含依赖：**第 5 步 `--backfill` 需要三列已存在，而建列发生在第 6 步部署新代码后的首次启动**。

   解决方式：`--backfill` 自身在开始前调用 `app.db` 的建表/建列例程（该例程幂等，重复执行无害），确保列存在后再回填。切换手册中须写明这一点，否则第 5 步会因列不存在而失败。
